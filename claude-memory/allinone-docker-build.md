An **all-in-one single-container** image (`docker/allinone/`), distinct from the multi-container `Dockerfile`/`docker-compose.yml`, meant to be `docker save`'d and transferred to a separate x86_64 production box for real users. Postgres 15 + nginx + supervisord + Ollama with `granite4.1:3b`+`:8b` baked into an image layer + the full app stack. AI defaults ON here (`MOBINSPECT_AI_ENABLED=1`, base `http://127.0.0.1:11434` loopback). 3 persistent **named** volumes (not bind mounts, so Docker copies image content on first mount): `/var/lib/postgresql/data`, `/usr/share/ollama/.ollama`, `/home/mobinspect/.MobInspect`. Runs as root; supervisord drops gunicorn/qcluster to `mobinspect`, Ollama to `ollama`. See [[ai-integration-implemented]], [[local-ai-enhancement]], [[docker-64-ai-fix]] (the multi-container analog), [[airgap-offline-readiness]].

**Bugs fixed while building it (affect the EXISTING multi-container `Dockerfile`/`scripts/dependencies.sh` too):** (1) JADX was never actually baked into ANY image — `tools_download` ran before `COPY . .` made the package importable, silently swallowed (no `set -e`), so the app fell back to downloading JADX at runtime (breaks air-gap). Fixed: JADX install moved to a `RUN` after `COPY . .` with a hard-fail check. (2) PDF/wkhtmltopdf `.deb` shipped broken unless `TARGETPLATFORM` was passed — `dependencies.sh` now falls back to `uname -m` and has `set -e`. (3) `su mobinspect -c` silently execs `/bin/false` (that user's shell) → must use `su -s /bin/bash mobinspect -c`. (4) postgres binary is 3 levels deep (`-maxdepth 3`). (5) Ollama installer doesn't create the `ollama` user in a non-systemd build → `useradd --system` first. (6) `zstd` needed in apt list. (7) `pkill -f "ollama serve"` matched the build's own RUN shell → use `pkill -x ollama`. Cross-build model bake: `ollama pull` of the 5.3GB 8B model dies with `unexpected EOF` under QEMU → instead `COPY --from=ollama-cache` a pre-pulled local cache (blobs are sha256-content-addressed, arch-independent).

**App-code bugs found during E2E testing — fixed WITH tests:**
1. `mobinspect/MobInspect/views/api/api_middleware.py`: every `/api/v1/*` view reads only `request.POST`, so a `Content-Type: application/json` body got a bogus **422 Missing Parameters**. New `_merge_json_body_into_post()` mirrors a flat JSON object into `request.POST` (json-only — never touches multipart uploads, silent no-op on bad/empty/non-dict, pins `request._files`). `request.POST = q` is LEGAL on Django 6.0.3 (`WSGIRequest` defines `POST = property(_get_post, _set_post)`), no 500 risk. + `test_cov_api_middleware.py`.
2. `mobinspect/StaticAnalyzer/views/android/views/manifest_view.py`: a bare `/manifest_view/<md5>/` with no `?type=` raised `MultiValueDictKeyError` → generic **500**; now `request.GET.get('type', 'apk')`. + `test_cov_manifest_view.py`.

**The 4 acceptance questions, EMPIRICALLY tested on the running arm64 container:**
- **500MB APK upload?** App guard = 500MB (`MOBINSPECT_MAX_UPLOAD_SIZE_MB=500`; `home.py oversize_message()` rejects `file.size>500MB` with "File exceeds the 500MB upload size limit!"; `DATA_UPLOAD_MAX_MEMORY_SIZE=550MB`). BUT the SHIPPED image's nginx caps at **256M** → 256–500MB APKs get a raw nginx **413** before Django. Proven: 260MB→413 on the stock image; after hot-reloading the fixed 550M nginx, 260/300MB pass nginx→Django and 520MB → the app's own 400 "exceeds 500MB" message (not a 413). **So: YES up to 500MB, but ONLY after a rebuild bakes the 550M nginx — the current image still 413s >256MB.** Gotcha: `nginx -s reload` is graceful, so a request fired right after a reload can still hit the old workers/limit and 413 spuriously; confirm with `nginx -T | grep client_max_body_size`.
