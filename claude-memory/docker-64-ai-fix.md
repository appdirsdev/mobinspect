The full MobInspect stack runs in Docker on **192.168.3.64** (`~/mobinspect-deploy/`, compose: postgres+ollama+mobinspect+worker+nginx). Verified end-to-end working 2026-07-20 (AVD runs separately — not in this stack). See [[prod-deployment-2026-07-14]] (.65 = the live/OVF box, do NOT touch its codebase) and [[ai-integration-implemented]].

**Persistent data layout (2026-07-22 — converted mihome to a bind-mount for parity with the DB, per user request "make mobinspect data persist like the database even if docker restarted"):** TWO host bind-mounts under `~/mobinspect-deploy/data/`, both survive restart/recreate/reboot AND `docker compose down -v`: (1) `./data/postgres` → `/var/lib/postgresql/data` (DB: scan rows, RBAC, AI enrichment); (2) `./data/mihome` → `/home/mobinspect/.MobInspect` (ALL MobInspect runtime data — `UPLD_DIR`/`DWD_DIR` = `.MobInspect/uploads`,`/downloads`, plus the image-baked `tools`/JADX, `signatures`, `secret`, `config.py`). AI models stay in the `mobinspect_ollama` NAMED volume (~7G, re-pullable; persists across restart/recreate/reboot but NOT `down -v`). **Migration gotchas if ever redone:** the bind-mount must be `chown -R 9901:9901` (the container's `mobinspect` uid=USER_ID from the Dockerfile) or the app can't write; and you must copy the ENTIRE old `.MobInspect` (not just uploads) — a bind-mount does NOT get the named-volume "copy image content on first mount" behavior, so an empty bind-mount would SHADOW the baked-in JADX/tools and break decompilation. Verified: existing 10 scans + fresh upload+scan+PDF all work, and everything survived a full `docker compose down && up -d` (containers destroyed) with the scan data intact.

**Why AI showed "model not connected" — two independent causes, both fixed via env only (no code change, existing image):**
1. **0 `ModelIntegration` rows.** The `GraniteClient` falls back to `MOBINSPECT_AI_BASE_URL` env and works, but the dashboard "Connected" status keys off `ModelIntegration.last_status`. Fix: create+probe a `generate` and a `classify` row (`update_or_create(role=...)` + `RBAC.views._apply_model_probe(integ)`), base_url `http://ollama:11434`, model `granite4.1:3b`. `_apply_model_probe` hits `/api/tags` and sets `last_status='connected'`. Both roles can be active at once (model_save does NOT call set_active). Integrations page: `/rbac/integrations/adb/`.
2. **The real generation failure (non-obvious trap):** `llm/client.py generate()` sends Ollama `"stream": false` (whole response buffered) while `requests` runs `stream=True`, where `MOBINSPECT_AI_READ_TIMEOUT` is the **time-to-first-byte**. First byte only arrives after the FULL generation. This Xeon E5-2620 v2 has **no AVX2 → granite4.1:3b ≈ 5 tok/s idle** (measured via `ollama run --verbose`), so a 1200-token report ≈ 240s → default 60s read timeout → `ReadTimeout` → `generate()` returns None → "AI failed". Also default `TOTAL_BUDGET=300` skipped pipeline stages 3-4.

**The env fix (in compose x-mi-env):** `MOBINSPECT_AI_READ_TIMEOUT=600`, `MOBINSPECT_AI_TOTAL_BUDGET=1200`, `MOBINSPECT_AI_KEEP_ALIVE=30m`, `MOBINSPECT_AI_CONNECT_TIMEOUT=10`. Full 4-stage `ai_enrich_task(Diva)` then completed in ~10.5 min, `STATUS=done`, coherent/accurate report. Any no-AVX2 / slow-CPU target needs the same widened timeouts.

**Two deploy gotchas hit:**
- **nginx 502 after recreating the mobinspect container:** nginx caches the upstream IP at config load (`upstream { server mobinspect:8000; }`); a recreated mobinspect gets a new IP → stale → 502 on everything. Fix: `docker compose restart nginx` after any mobinspect recreate.
- **worker shows "unhealthy":** the image's baked `HEALTHCHECK curl localhost:8000/healthz` can't pass on a django-q worker (no HTTP server); worker has no procps either. Fix: `healthcheck: {disable: true}` on the worker service (restart:unless-stopped still recovers crashes). Worker liveness proved by enqueue→OrmQ 1→0 (save_limit=0 so `fetch()` returns None even on success — use queue drain, not fetch/Success count).

**Verified working on .64:** login (http:80 302 / https:443), AI dashboard `/ai_dashboard/<md5>/` renders full inline report, Integrations Connected, PDF export (%PDF 153KB, no tamper error), scorecard (37), search, report_json, RBAC (no-key 401 / admin-key 200), worker scan_queue. **2026-07-22 — third deploy gotcha, root-caused and fixed at the source (not a workaround):** a rebuild from a genuinely fresh `git clone` (as opposed to reusing a local checkout someone had already run `tailwind-build.sh` in) shipped an app with **zero CSS** — every page loaded unstyled, browser console showed a 404 on `app.css` rejected as the wrong MIME type (Django's branded 404 HTML came back instead of a stylesheet). Root cause: `mobinspect/static/mobinspect/css/dist/app.css` is gitignored (generated Tailwind output, never committed by design — see `mobinspect/static/mobinspect/.gitignore`), and neither the `Dockerfile` nor `entrypoint.sh` ever built it. The *previously*-working image only had CSS because whoever built it happened to run the tailwind build locally first — an invisible, undocumented manual step. **Fixed at the source**: the `Dockerfile` now runs `./scripts/install-tailwind.sh && ./scripts/tailwind-build.sh --minify` itself right after `COPY . .` (Tailwind's content-scanning needs the full templates/static tree, so it must run after the copy — building CSS earlier alongside the JDK/JADX dependency step won't see the templates yet), then deletes the ~40MB Tailwind CLI binary in the same layer (build-time tool only). `.dockerignore` also excludes `tools/tailwindcss*` so a locally-cached binary never rides along either way. `docker build .` is now fully reproducible from a bare `git clone` — verified twice: once showing the bug (missing CSS from a fresh clone with the old Dockerfile), once showing the fix (CSS present, 63KB minified, image size unchanged since the binary is cleaned up in-layer) from an equally fresh clone with the new Dockerfile. Committed `9bebbff`.
