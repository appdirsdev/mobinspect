{# ─────────── Getting started ─────────── #}

{% icon "upload-cloud" size=16 %} Getting started

This platform performs automated static and dynamic security analysis of mobile applications. Upload an app once and it is decompiled, inspected against a large rule set covering permissions, manifest configuration, network security, embedded secrets, known-vulnerable libraries, and insecure code patterns — then summarized into a single report with a security score, so your team can triage findings without reading source code line by line.

It is built for application security teams, mobile developers doing self-review before release, and SOC/NOC analysts who need a fast, consistent read on an app's risk posture.

PlatformSupported file types
AndroidAPK · AAB · XAPK · JAR · AAR · SO · source ZIP
iOSIPA · Mach-O / DYLIB · source ZIP (Xcode / Swift projects)
WindowsAPPX
{# ─────────── Running a scan ─────────── #}

{% icon "activity" size=16 %} Running a scan

  1. From New scan, drag a supported file onto the upload panel or click Choose file.
  2. The app is queued and analyzed automatically — no configuration required. You're redirected to the report once it starts.
  3. Once complete, the report page shows a security score, app metadata, and every analysis section, each with its own anchor in the section tab bar at the top of the report.
  4. Use Rescan to re-run analysis after a rule-set update, or Compare to diff two versions of the same app side by side.
  5. All past scans are listed under Scans, searchable by app name, package, file name, or hash.
{# ─────────── Understanding your report ─────────── #}

{% icon "file-text" size=16 %} Reading a report

Every report is organized into sections, navigable from the tab bar pinned to the top of the page. What each one covers:

SectionWhat it tells you
PermissionsEvery permission the app declares, with a plain-language explanation and a risk rating for each.
Network securityWhether traffic is encrypted, TLS/certificate pinning misconfigurations, cleartext-traffic exceptions.
Manifest / Info.plistApp-configuration issues — exported components without protection, debuggable builds, backup flags, ATS exceptions.
Code analysisInsecure coding patterns found in the decompiled or provided source — weak crypto, insecure storage, unsafe WebView settings, and similar.
ComponentsActivities, services, broadcast receivers, and content providers, flagging which are exported (reachable by other apps) and unprotected.
Libraries / SBOMEvery third-party library the app bundles, so you can cross-check versions against your own vulnerability tracking.
TrackersKnown analytics and advertising trackers detected in the binary.
SecretsHardcoded API keys, tokens, and credentials found in strings or source — always worth a manual look before shipping.
URLs / Emails / Server locationsEvery embedded URL and email address, plus the countries the app's declared endpoints resolve to.
FirebaseWhether an exposed Firebase database was detected and is publicly readable.

Findings you've already triaged can be suppressed per rule (or per rule + file) directly from the finding's row menu, so future rescans don't re-surface what you've already reviewed.

{# ─────────── Security score ─────────── #}

{% icon "gauge" size=16 %} Security score

Every report shows a 0–100 security score at the top. It is calculated deterministically from the findings on that specific scan — each finding deducts points according to its severity, and the total is banded into Passed, Low, Medium, High, or Critical. It is not an estimate or an AI opinion — the same findings will always produce the same score.

Analytics rolls this up across your whole scan history so you can track average score, issue volume, and trend over time.

{# ─────────── AI Dashboard ─────────── #}

{% icon "zap" size=16 %} AI Dashboard

Once a report finishes, an optional AI enrichment pass can read its findings and produce four extra views, available from the AI Dashboard button on the report page:

  • Executive summary — a plain-language recap of the app's overall risk posture, written for a non-technical stakeholder.
  • Secrets triage — a second pass over any detected secrets/credentials, helping distinguish likely-real exposures from test fixtures and false positives.
  • Risk classification — each risk dimension (network, permissions, platform & manifest, code, privacy & trackers, secrets) rated on a fixed none/low/medium/high/critical scale, with a short rationale.
  • Anomalies & suggestions — patterns across the findings a reviewer might otherwise miss, each paired with a concrete next step.

The dashboard also shows an AI risk score out of 100 — this is computed server-side from the categorical risk ratings above, the same way the report's security score is computed; the model never outputs a number directly, so the score can't be prompted into being inflated or deflated.

The AI Dashboard is only reachable once enrichment has actually completed for that scan — if no AI report exists yet (or the model isn't configured), the button is hidden and the page redirects rather than showing an empty or broken view.

Enrichment runs against a model you host yourself (see Integrations below) — nothing leaves your network, so this works the same in a fully offline / air-gapped environment as it does online.

{# ─────────── Integrations ─────────── #}

{% icon "sliders" size=16 %} Integrations

The Integrations admin page connects the platform to services on your own network — nothing here reaches the public internet:

  • AI model connection — host, port, and model name for report generation and classification. Connections are restricted to private/loopback network ranges, and Test connection validates the exact values on the form before you save, so you always know a saved connection actually works.
  • Device / ADB connections — the host and port of an Android device or emulator used for dynamic analysis.

Both are scoped per role, so different teams can point at different model hosts or device pools without stepping on each other.

{# ─────────── Dynamic analysis ─────────── #}

{% icon "smartphone" size=16 %} Dynamic analysis

Beyond static analysis, apps can be installed and exercised on a connected Android device or emulator to observe actual runtime behavior — API calls made, network requests sent, files written, and activities launched — which surfaces issues that only show up when the app is actually running. Start it from Dynamic in the sidebar once a device is connected under Integrations.

{# ─────────── Roles & permissions ─────────── #}

{% icon "shield" size=16 %} Roles & access

Access is role-based: every user is assigned a role, and every role is an explicit set of permissions. Four roles ship by default and can be adjusted or extended from Roles:

RoleTypical use
AdministratorFull access, including user, role, and integration management.
Security AnalystRuns scans, triages and suppresses findings, uses dynamic analysis and the API.
ViewerRead-only access to scans, reports, and analytics.
API UserProgrammatic-only access for CI/CD pipelines — no interactive login features.

Every permission-gated action — including sign-ins, scan uploads, and integration changes — is written to the Audit log for traceability.

{# ─────────── API access ─────────── #}

{% icon "key" size=16 %} API access

Every scan action — upload, scan, fetch a report as JSON or PDF, search, delete — is available over a REST API, so it can be scripted into a CI/CD pipeline. Generate a personal API key from API keys, then see the full endpoint reference and request examples on the API documentation page.
