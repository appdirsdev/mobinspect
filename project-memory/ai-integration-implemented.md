**Architecture (all ADDITIVE — scan pipeline apk.py/ipa.py/static_analyzer.py/db_interaction.py/sast_engine.py are UNTOUCHED, verified via git diff):**
- **Separate AI Dashboard page** (`/ai_dashboard/<md5>/`), NOT embedded in the scan report/dashboard — reached via an "AI Dashboard" button (icon `zap`) added to the 4 report headers (android/ios binary+source). If AI breaks, the scan dashboard never references it. NOT in the PDF.
- **Background, decoupled from the scan queue:** after a scan completes, a django-q `post_execute` signal receiver (`llm/signals.py`, registered via new `StaticAnalyzer/apps.py` `ready()`) launches enrichment in a **daemon THREAD** (`tasks.enrich_in_background`), NOT on the scan queue. Local footprint is just HTTP to the remote model box, so it never occupies a scan worker. `MOBSF_ASYNC_WORKERS` default changed 2→**1** (serialize scans, one static report at a time).
- **New files:** `mobsf/StaticAnalyzer/views/common/llm/{__init__,client,prompts,tasks,signals,views}.py`, `apps.py`, migration `StaticAnalyzer/0002_aienrichment.py`, RBAC migration `0010_add_ai_view_permission.py`, templates `_ai_analysis.html` + `ai_dashboard.html`. **Edited existing (additive only):** settings.py (MOBINSPECT_AI_* block + Q_CLUSTER workers=1), urls.py (defensive AI routes, try/except so broken AI import can't break routing), RBAC 0002 seed (+admin.ai.view), models.py (AIEnrichment: MD5 PK + STATUS + EXEC_SUMMARY + FINDING_EXPLANATIONS list + SECRETS_TRIAGE + MODEL_USED), appsec.py (1-line: `len(secrets)>1`→`>0` single-secret bugfix), 4 report templates (+`{% load rbac %}` + button).

**ADMIN-ONLY:** new RBAC perm `admin.ai.view` (granted to Administrator role only). `ai_dashboard` page uses `@require_permission('admin.ai.view')` (403 for others); `ai_report` htmx endpoint returns 204 for non-admins; the button is gated `{% can 'admin.ai.view' %}`.

**GUARDRAILS (input is attacker-controlled from a possibly-malicious app):** `prompts.py` `sanitize_untrusted` (NFKC + strip bidi/zero-width/control + chat tokens `<|..|>`/`### Instruction`), `<untrusted_app_data>` delimiting, secret **redaction** (masked token, never the literal); `sanitize_output` strips URLs/markdown-links/score-claims + bidi from MODEL OUTPUT too. `client.py` GraniteClient: enclave-only endpoint (loopback/RFC1918, reject public — SSRF guard), `allow_redirects=False`, `(connect,read)` timeouts, streamed `MAX_RESPONSE_BYTES` cap, `num_predict` cap, never logs bodies, returns None on any failure. Deterministic `security_score` NEVER touched by AI.

**Enrichment is now a 3-STAGE pipeline, 2026-07-12:** ai_enrich_task runs (1) GENERATION model → the 6-section report; (2) CLASSIFICATION model → secret triage (`SECRETS_TRIAGE`); (3) CLASSIFICATION model → per-dimension **risk classification** for a chart (`RISK_CLASSIFICATION`, new TextField + migration `StaticAnalyzer/0003`). All persist on AIEnrichment, re-viewable at `/ai_dashboard/<md5>/`. Risk chart = CSS bars in `_ai_analysis.html` (theme-aware `.mi-risk-*` colors in `ai_dashboard.html`). **GUARDRAIL (critical):** the AI never emits a numeric score — `build_risk_classification_prompt` asks for CATEGORICAL levels over 6 FIXED dimensions (RISK_DIMENSIONS) from a FIXED enum (RISK_LEVELS none..critical); `parse_risk_classification` is deterministic — a known dimension + allowed level only, else 'unknown', so the model can't inject a dimension or a numeric score; the deterministic security_score stays authoritative. Stages 2+3 are decoupled (fail/raise → STATUS stays 'done', report intact) and gated by a NOW-ENFORCED `MOBINSPECT_AI_TOTAL_BUDGET` deadline (was defined-but-unused). Classify with no classify row now reuses the GENERATE host (was dialing localhost + failing every scan). `MOBINSPECT_AI_TRIAGE_TOKENS`=400 caps stages 2/3. 419 llm tests pass. Getting the enrichment RELIABLE on the slow .183 CPU took fixing four gotchas, all now resolved: **(1) `keep_alive` string bug** — the client sends `keep_alive` from `MOBINSPECT_AI_KEEP_ALIVE` as a STRING; ollama rejects `"-1"` with `HTTP 400 "time: missing unit in duration"`. Use a unit'd duration (set `MOBINSPECT_AI_KEEP_ALIVE=8760h`) or a NUMERIC `-1` (only works in raw curl, not via the client). **(2) num_ctx reload trap** — the client always sends `num_ctx=8192`; if a model is resident at a DIFFERENT context it gets fully RELOADED (~15s) on every enrichment call. Must pin models at ctx 8192 to match. **(3) request backlog** — when a report exceeds the client read timeout, ollama keeps generating server-side; with `OLLAMA_NUM_PARALLEL=1` the next request QUEUES behind it → cascading 180s timeouts. Clear via `systemctl restart ollama`. **(4) cold-load flakiness** — the 5.3GB 8B loads in ~15s when page-cache-warm but can take minutes (or exceed ollama's 5m `OLLAMA_LOAD_TIMEOUT`) cold; the first enrichment after an ollama restart would fail. FIX: a new **`ollama-preload.service`** on .183 (`/usr/local/bin/ollama-preload.sh`, `After=/Requires=/PartOf=ollama.service`, `WantedBy=multi-user.target`, `TimeoutStartSec=900`) that waits for the API then loads BOTH models at ctx 8192 pinned (`keep_alive:-1` numeric) on every ollama start/boot. ollama tuning drop-in updated: `OLLAMA_MAX_LOADED_MODELS=2` (both 8B+3B resident ~9.5GB of 47GB — user OK'd pinning models in RAM), `OLLAMA_KEEP_ALIVE=-1`, `NUM_PARALLEL=1`. **8B warm rate ≈3.5 tok/s** on this no-AVX2 CPU; a 400-tok report = ~114s (66s margin under the 180s per-call read timeout).
