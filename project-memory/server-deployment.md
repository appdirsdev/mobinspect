1. `poetry export -f requirements.txt --only main --without-hashes -o /tmp/req.txt` (Poetry 1.8.4 local), scp + `.venv/bin/pip install -r` on server.
2. `rsync -az --delete --exclude .git --exclude test_files --exclude .venv --exclude __pycache__ --exclude '*.pyc' --exclude .env.postgres ./ mobinspect@10.249.54.76:MobInspect/` — macOS ships **openrsync**: `--info=stats1` is unsupported (prints usage, syncs nothing); use `--stats`. Verify with sha256 spot-checks + file counts.
3. `sudo systemctl restart mobinspect-web mobinspect-qcluster` (migrate runs via ExecStartPre).

**GOTCHA — gunicorn 25.1.0 fork-deadlock (cost an hour):** this fork pins gunicorn 25.1.0 which runs a **control-socket thread** in the master (`--control-socket`, default `./gunicorn.ctl`). At `--log-level=info`, the master's socket thread can hold the logging handler lock exactly when the arbiter forks; the worker child then deadlocks INSIDE its first `log.info("Booting worker…")` (py-spy: stuck at `logging emit` / futex, ~20 MB RSS, no log lines) and with `--timeout=3600` it stays wedged ~1 h while the socket accepts but never answers (curl → timeout even on localhost). It looked like an env-var/AmbientCapabilities problem but binary-search + py-spy proved caps were innocent. **Fix baked into the unit:** `--log-level=warning` (filters both racing emits) + `--control-socket /run/mobinspect/gunicorn.ctl` (`RuntimeDirectory=mobinspect`). 3/3 restarts now serve within ~4 s. If a future boot ever hangs: `py-spy dump --pid <worker>` (py-spy is installed in the server venv).

**GOTCHA #2 — billiard SAST deadlock (async scans hang forever):** with `MOBSF_ASYNC_ANALYSIS=1` on Linux, `sast_engine.get_multiprocessing_strategy()` picks **billiard** (fork) inside the threaded qcluster worker → fork-inherited locks → pool children freeze at 0 % CPU mid `java_source` SAST, both workers wedge, queue stalls (timeout 3600 s, max_attempts 1 = no self-heal). **Fix baked in:** drop-in `mp.conf` on BOTH units sets `MOBSF_MULTIPROCESSING=thread` (a supported value — Windows async uses it). Verified: DIVA apk + source-zip scans complete end-to-end.
**Stuck-queue recovery:** a killed/deadlocked scan leaves `EnqueuedTask` rows that block re-enqueue for `ASYNC_ANALYSIS_TIMEOUT` (60 min) — the report URL just 302s to `/tasks?q=queued` WITHOUT enqueueing (async_task.py `queued_recently` gate). Sanctioned reset: `manage.py clear_tasks` (wipes django-q Task/OrmQ + EnqueuedTask only), then re-GET `/static_analyzer/<md5>/` to re-trigger. Raw DB deletes over ssh get blocked by the permission classifier; `clear_tasks` is the right tool anyway.
